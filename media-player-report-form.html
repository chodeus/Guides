Media Player Report Form

Testers file a report through a GitHub issue form. A workflow turns it into a pull request straight away. A maintainer only reviews and merges, and the merge puts the results in the table.

How a report reaches the table

  1. Tester

    Fills in the form

    The issue opens with the Type: Media Player Report label and the screenshots attached. Opening it starts the workflow.

  2. GitHub Actions

    Comments on the issue

    The comment says what will change: which row, which cells and which notes. A name that is close to an existing row gets a hint, for example “No row is named Apple TV 4K. Did you mean Apple TV (4K)?”

    No format has a result? The comment says so, and no PR opens.
  3. GitHub Actions

    Builds the table change

    • Finds the Device + Player/Product row, or adds a new one. Rows sort by Device, and the order within a device stays.
    • Fills blank cells with ✅ or ❌. A result that clashes with a filled cell is left alone.
    • Turns each note into hover text. A note that matches an existing one reuses it.
    • Adds the credit note with the issue link, then runs the repo's markdownlint.
  4. GitHub Actions

    Opens the pull request

    The PR says Closes #N and lists every cell it filled and every clash it skipped.

  5. Tester or maintainer

    Fixes mistakes in the issue only if needed

    Editing the issue rebuilds the PR and updates the comment. Nobody edits the table text by hand.

  6. Maintainer

    Reviews and merges

    The merge puts the results in the table, the issue closes and the site deploys.

  7. GitHub Actions

    Keeps the other reports current

    Every other open report PR is rebuilt on top of the updated table, so they never conflict with each other.

A maintainer only has to merge, plus fix a report in the issue when needed. A junk report becomes a PR to close. The label follows the Type: style the repo already uses, and the workflow follows the same pattern as the Add Release Group workflow.
