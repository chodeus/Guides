Media Player Reports

Three pull requests put the Tested Media Players table on the TRaSH Guides site, and let testers add their own results to it. This page explains what each pull request adds, how a tester's report becomes a pull request, and what a maintainer does with that pull request.

Words used on this page

The table
The Tested Media Players table. It is stored in one file, docs/Plex/tested-media-players.md, in the TRaSH-Guides/Guides repository on GitHub. After pull request 1 is merged, the site shows it at trash-guides.info/Plex/tested-media-players/.
A report
A GitHub issue that a tester opens with the Media Player Test Report form. One report holds the results for one device and one player.
A report pull request
The pull request that the workflow opens for one report. It changes only the table file.
The workflow
The GitHub Actions workflow named Maintain: Media Player Report, in .github/workflows/media-player-report.yml. It runs by itself; nobody has to start it.
master
The main branch of TRaSH-Guides/Guides. The site is built from master.

The three pull requests

  1. The table page

    Adds the table file, docs/Plex/tested-media-players.md, with its own stylesheet and script. It adds a link to the new page on the What does my Media Player Support page, and it turns on footnote tooltips in mkdocs.yml. The table file is a normal Markdown page, and you can edit it like any other page.

    Preview the page

  2. The report script and its check

    Adds scripts/media-player-report.py, which copies the results of one report into the table file. It also adds the Validate: Media Player Report workflow. That workflow runs the script's tests, and it checks the layout of the table file in every pull request that changes the table.

    See what the script changes

  3. The report form and the workflow

    Adds the Media Player Test Report issue form, and the workflow that makes a report pull request from each report.

    Open the form. This copy of the form is in chodeus/Guides, a test copy of the repository. That copy has the form only, not the workflow, so submitting the form there does not open a pull request.

Merge them in this order: 1, then 2, then 3. Before you merge pull request 3, change one setting. In the TRaSH-Guides/Guides repository on GitHub, click Settings, then Actions, then General. Under Workflow permissions, tick Allow GitHub Actions to create and approve pull requests, then click Save.

Without this setting, the workflow cannot open pull requests, and each report gets a "Something went wrong" comment instead.

How a report becomes a pull request

  1. Tester

    Posts the test results on Discord

    On the TRaSH Guides Discord server, in the suggestions channel, with the test media players tag. People can discuss the results there.

  2. Tester

    Fills in the report form on GitHub

    The form is in the TRaSH-Guides/Guides repository on GitHub. To open it, click Issues, then New issue, then Media Player Test Report. The What does my Media Player Support page on the site also links to it. The tester needs a GitHub account.

    The tester fills in Device, Player/Product, the link to their Discord post, and at least one result (✅ Yes or ❌ No). All other fields are optional. When the tester submits the form, GitHub opens a new issue. Its title starts with [Media Player], unless the tester changes it.

  3. GitHub Actions

    Writes the results into the table file

    The workflow starts by itself when the issue opens. It changes the table file, docs/Plex/tested-media-players.md, on a new branch. Nothing changes on master or on the site yet.

    • It looks for a row with the same Device and the same Player/Product. If there is no such row, it adds a new row, sorted by Device.
    • It fills only empty cells and ❔ (untested) cells. If a cell already has ✅ or ❌ and the report has a different result, it does not change that cell. It lists the difference for a maintainer.
    • It adds a footnote that credits the tester: their name, their Discord post, the date, their TV or AVR (if they gave one), and a link to the issue. For each note the tester wrote about a result that it adds, it adds one more footnote.
    • It checks that the table file still has the correct layout.
    Is something wrong in the report? For example, a required field is empty, or no format has a result. Then the workflow does not open a pull request. Its comment on the issue tells the tester what to fix.
  4. GitHub Actions

    Opens a report pull request

    The branch name is feat/plex-media-player-report-issue- followed by the issue number. The pull request lists every change. It ends with Closes # and the issue number, so merging it closes the issue. The workflow also starts the pre-commit check on the pull request, because master requires that check.

  5. GitHub Actions

    Comments on the issue

    The comment thanks the tester, links to the pull request and lists the changes. When the workflow runs again for the same issue, it edits this comment. It does not add a new one.

  6. Maintainer

    Reviews the report pull request

    The maintainer opens the pull request on GitHub and checks the changes. Then the maintainer merges it, fixes the report, or rejects the report. See What to do with a report.

  7. GitHub Actions

    Updates the other reports

    Merging the pull request changes the table file on master and closes the issue. The normal site deploy then shows the new results on the site.

    After the merge, the workflow builds every other open report pull request again, on top of the new table. This way, none of them stays in conflict.

What to do with a report

Is correctMerge the report pull request.The table changes on master, the issue closes, and the workflow updates the other open report pull requests.
Has a typing mistake or a wrong resultEdit the issue. Do not edit the pull request (see the note below this table).The workflow builds the pull request again from the issue, and it edits its comment on the issue.
Spells a device or player differently from the tableEdit the issue. Copy the exact name from the table into the Device or Player/Product answer. Is spam, a duplicate, or rejectedClose the issue.The workflow closes the pull request with a comment and deletes its branch. If you reopen the issue later, the workflow builds the pull request again.

How to edit an issue

The tester and any maintainer can edit a report. Open the issue on GitHub. At the top right of the first post (the report itself), click the ⋯ (three dots) button, then click Edit.

Each answer is below its question, and each question is a line that starts with ###. Change the text below the question. Then click Save (on some GitHub pages, this button is called Update comment). A result must be exactly ✅ Yes, ❌ No or Not tested. For example, this part of a report sets the Device name and the MEL result:

### Device

Chromecast Google TV

### MEL

❌ No

If you edit the pull request instead of the issue: the workflow builds a report's branch again every time the issue is edited, and every time the table changes on master. Merging any other report changes the table. Each time this happens, your changes on the branch are deleted.

So, put the fix in the issue, or edit the pull request and merge it immediately. For example, to use the report's result for a cell that differs from the table, you can change that cell in the pull request and then merge it immediately.

Editing the table yourself

You can edit the table file, docs/Plex/tested-media-players.md, yourself, like any other page. But the report script can only read the table if the file keeps the layout that the script writes. So the Validate: Media Player Report workflow checks the layout in every pull request that changes the table file. These are the rules:

  • Do not change the header row of the table.
  • Each row of the table is on one line and has 22 cells. There are no empty lines inside the table.
  • Every footnote that the table uses has a footnote text, and every footnote text is used. The footnote texts are in the same order as their first use in the table. If they are not, the footnote numbers on the page are out of order.
  • There are no empty lines between footnote texts. There is one empty line before the abbreviations (the lines that start with *[).
  • The line ///Footnotes Go Here/// stays below the table.

the columns are […], the report script expects […]Someone changed the header row. See Adding or renaming a column, below.

Do not merge a change to the table file while this check fails. After every change to the table on master, the workflow builds every open report pull request again. If the script cannot read the table, every open report gets a "Something went wrong" comment. When you fix the table, the workflow builds them all again.

Adding or renaming a column

Change these places in the same pull request:

  • The header row of the table, and the row below it. For a new column, also add an empty cell to every row.
  • The FORMATS list at the top of scripts/media-player-report.py.
  • The form, .github/ISSUE_TEMPLATE/media-player-test-report.yml: the dropdown for the format, and its line in the notes box.

The check and the tests fail until the table, the script and the form all match.

Running the workflow yourself

Open the TRaSH-Guides/Guides repository on GitHub and click the Actions tab. In the list of workflows on the left, click Maintain: Media Player Report. On the right, click Run workflow.

To build one report pull request again, type the issue number in the box. To build every open report pull request again, leave the box empty. Then click the green Run workflow button. Do this after you fix the cause of a failed run.

Other things to know

  • A pull request that GitHub Actions opens does not start other workflows. So the workflow starts the pre-commit check itself. Other pull request workflows do not run on report pull requests.
  • The workflow creates the Type: Media Player Report label when the first report arrives. The stale bot never closes issues that have this label.
  • The footnotes that the script adds have names that start with report- and the issue number, so you can see which footnotes came from a report.
  • If the tester leaves Tested by empty, the credit uses their GitHub name. If the tester leaves Date of test empty, the credit uses the month when the issue was opened.
  • When the workflow builds every open report pull request again, it handles at most 256 reports.
