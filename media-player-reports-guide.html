Media Player Reports

Three pull requests move the Tested Media Players sheet onto the site and let testers add their own results. This page shows what each one adds, how a test report becomes a pull request, and what a maintainer does with it.

The three pull requests

  1. The table page

    Adds docs/Plex/tested-media-players.md with its stylesheet and script, links it from What does my Media Player Support, and turns on footnote tooltips. It is a normal page: edit it like any other.

    Preview the page

  2. The report script and its check

    Adds scripts/media-player-report.py, which writes one report into the table, and the Validate: Media Player Report workflow. That workflow runs the script's tests and checks the table layout on every pull request that changes the table.

    See what a report changes

  3. The report form and its workflow

    Adds the Media Player Test Report issue form and the Maintain: Media Player Report workflow, which turns each report into a pull request.

    Open the form (on a test copy of the repo)

Merge them in this order. Before merging the third, go to Settings → Actions → General → Workflow permissions and tick Allow GitHub Actions to create and approve pull requests. Without it, reports get a "Something went wrong" comment instead of a pull request.

How a report becomes a pull request

  1. Tester

    Posts the test on Discord

    In the suggestions channel with the test media players tag, so people can discuss the results.

  2. Tester

    Fills in the form

    Device, Player/Product, the Discord thread link and at least one ✅ or ❌ result. Everything else is optional. Submitting opens an issue titled [Media Player] ….

  3. GitHub Actions

    Adds the results to the table

    • Finds the row with the same Device and Player/Product, or adds a new row in Device order.
    • Fills only empty cells and ❔ (untested) cells. A result that differs from a filled cell is left alone and listed for a maintainer.
    • Adds a credit footnote (tester, Discord thread, date, TV/AVR, link to the issue) and a footnote for each note on a result it adds.
    • Checks the table layout.
    Report can't be read? For example, a required field is empty or no format has a result. The comment lists what to fix, and no pull request opens.
  4. GitHub Actions

    Opens the pull request

    On the branch feat/plex-media-player-report-issue-<number>. The body lists every change and says Closes #<issue>. It also starts pre-commit, the required check, on the pull request.

  5. GitHub Actions

    Comments on the issue

    Thanks the tester, links the pull request and lists the changes. Later runs edit this one comment instead of adding new ones.

  6. Maintainer

    Merges it, fixes it, or closes it

    See What to do with a report.

  7. GitHub Actions

    Keeps the other reports current

    The merge closes the issue. Every other open report pull request is then rebuilt on top of the new table, so none of them stays in conflict.

What to do with a report

The reportDo thisWhat happens
Looks rightMerge the pull request.The table updates, the issue closes and the other reports rebuild.
Has a typo or a wrong resultEdit the issue, not the pull request.The pull request is rebuilt from the issue, and the comment updates.
Spells a device or player differently from the tableEdit the issue and copy the name from the table. When a name is close, the comment asks "Did you mean …?"The results move to the existing row instead of a new one.
Has a result that differs from the tableDecide which is right. To keep the table's, merge as it is. To use the report's, change that cell by hand.The pull request never changes a filled cell.
Is junk, a duplicate, or turned downClose the issue.Its pull request closes with a comment and its branch is deleted. Reopening the issue builds it again.
Needs a fix from the testerWait for the tester to edit the issue, or edit it yourself.The comment lists what to fix. No pull request opens until then, or the earlier one keeps its results.
Got a "Something went wrong" commentOpen the workflow run that the comment links to.The log says why. It is usually the table layout: see Editing the table by hand.

Editing an issue

On the issue, open the ⋯ menu on the first post and choose Edit. Each answer sits under its question, which is a ### heading. Change the text under the heading, then save. A result is ✅ Yes, ❌ No or Not tested.

### Device

Chromecast Google TV

### MEL

❌ No

If you edit the pull request instead. Commits pushed to a report's branch last only until its next rebuild. A rebuild happens whenever the issue is edited or the table changes on master, and merging any other report changes the table.

So put the fix in the issue, or edit the pull request and merge it straight away. Editing the pull request is the quick way to take the report's side on a differing cell: change the cell, then merge.

Editing the table by hand

docs/Plex/tested-media-players.md is a normal page, and hand edits are fine. The report script needs the layout it writes, so Validate: Media Player Report checks every pull request that changes the table:

  • The header row stays as it is.
  • Every row is one line with 22 cells, and the table has no blank lines inside it.
  • Every footnote is used and has text. Footnote texts follow the order they are first used in, or their numbers come out of order.
  • No blank lines between footnotes, and one blank line before the abbreviations.
  • ///Footnotes Go Here/// stays below the table.
The check saysFix
line 31 is a table row after the table ended at line 29; remove the break above itRemove the blank line inside the table.
the row for Roku Ultra 4640x has 21 cells instead of 22That row is missing a |.
footnote new-note is used but has no textAdd [^new-note]: … below the footnote marker, or remove the reference.
footnote chromecast-dtsx has text but isn't usedRemove its text, or put the reference back.
footnotes must be listed in the order they're first usedMove the footnote text to match the order in the table.
line 48 isn't in the layout the report script writesRemove the blank line between footnotes, or put back the one before the abbreviations.
the columns are […], the report script expects […]The header row changed. See adding a column below.

Don't merge a table change while this check fails. Every open report is rebuilt after each table change. If the script can't read the table, each of those issues gets a "Something went wrong" comment. Fixing the table rebuilds them again.

Adding or renaming a column

Change three places together: the table's header row, the FORMATS list at the top of scripts/media-player-report.py, and the form (the format's dropdown and its line in the notes box). The check and the tests fail until all three match.

Running it by hand

Go to Actions → Maintain: Media Player Report → Run workflow. Enter an issue number to rebuild that report, or leave it blank to rebuild every open report. Use it after fixing whatever made a run fail.

Good to know

  • Pull requests opened by GitHub Actions start no workflows of their own, so the workflow starts pre-commit on each one. Other pull request workflows don't run on report pull requests.
  • The workflow creates the Type: Media Player Report label on the first report. The stale bot skips issues with that label.
  • Footnotes the script adds are named report-<issue>-…, so you can tell them from hand-written ones.
  • A blank Tested by uses the tester's GitHub name, and a blank Date of test uses the month the issue was opened.
  • Rebuilding every open report covers up to 256 reports.
